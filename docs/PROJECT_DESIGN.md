## 1. 项目概述

### 1.1 项目背景

目前，智能手机仍然是短信消息的主要接收终端。用户在使用多台电脑、平板设备或远程工作站时，往往难以统一管理短信消息。

与此同时，营销短信、虚假通知、钓鱼链接及其他低价值信息占据了短信收件箱，影响重要消息的正常获取。

现有解决方案主要存在以下不足：

1. 跨设备同步依赖第三方云服务，用户对数据缺乏完整控制。
2. 传统短信过滤主要依赖关键词或号码黑名单，面对不断变化的短信模板适应能力有限。
3. 一些智能分类方案需要将完整短信正文提交给第三方 AI 服务。
4. 部分短信转发工具缺少可靠的离线同步、设备权限管理和安全审计机制。
5. 短信拦截、分类与跨设备管理通常属于不同应用，缺乏统一的处理流程。

PrivRelay 旨在构建一个集**短信接收、智能分类、自动拦截、可靠同步、隐私保护和多设备管理**于一体的软件平台。

### 1.2 项目目标

开发一套能够由用户自行部署和管理的跨设备短信系统，实现：

- 手机短信自动采集与统一管理。
- 基于自训练模型的短信智能分类。
- 按用户配置自动拦截营销及高风险短信。
- 重要短信跨设备实时同步。
- 网络中断后的可靠补发与消息去重。
- 多终端授权、访问控制及安全管理。
- 本地数据存储、用户纠错和模型版本管理。

系统采用 Local-first 和 Self-hosted 的设计思想，尽可能减少对外部商业服务的依赖。

### 1.3 项目定位

PrivRelay 不只是一个短信转发器，也不只是一个 AI 垃圾短信识别工具。

它是一个完整的**隐私优先型智能消息管理平台**。

其重点在于将已有短信分类技术与分布式软件架构结合，解决实际的消息管理问题。

## 2. 已有技术基础

### 2.1 PrivateSMS-Classifier

项目已拥有独立开发的中文短信分类系统。

**现有仓库：**

https://github.com/dsclca12/PrivateSMS-Classifier

已具备的能力：

- 基于 hfl/rbt3 的中文文本分类模型。
- 六分类短信识别。
- INT8 ONNX 量化推理。
- ONNX Runtime CPU 部署。
- FastAPI 推理服务。
- 模型版本管理与评估模块。
- SQLite 人工反馈管理。
- Docker 容器化部署。
- 自动化测试与隐私数据发布隔离。

当前公开模型支持的分类如下：

| 类别 | 含义 |
|---|---|
| `personal` | 个人短信 |
| `otp` | 验证码 |
| `service` | 服务通知 |
| `transaction` | 交易通知 |
| `marketing` | 营销短信 |
| `suspicious` | 可疑短信 |
| `uncertain` | 低置信度拒绝分类结果 |

公开模型在 183 条合成测试消息上取得约 89.62% Accuracy 和 89.13% Macro-F1。

此外，开发者在真实短信使用环境下进行过实际体验，主观评价已具有较好的可用性，并认为可以进入自动拦截功能的开发阶段。

需要区分的是：真实使用体验支持当前模型进入产品集成，但尚不能等同于已获得独立、量化的生产环境误拦截率。

### 2.2 模型使用决策

**第一阶段不重新训练模型。**

直接复用现有 `rbt3-six-class` 模型作为第一版分类引擎。

保留原有的模型推理、管理和反馈代码，避免重复开发。

模型未来只在出现明显的错误分布变化、需要新语言支持或获得充分的新评估证据时，再考虑针对性优化。

### 2.3 自动拦截能力现状

当前仓库已经包含 `/sms/score` 接口，但公开模型配置了：

- `confidence_calibrated = false`
- `always_requires_review = true`

现有服务因此不会仅凭该模型的预测自动返回 `block`。

PrivRelay 的自动拦截模块需要新增独立的策略引擎和用户授权逻辑，不应通过简单删除原有保护条件实现。

## 3. 系统核心功能

### 3.1 Android 短信接收

系统通过 Android 客户端采集用户授权范围内的短信。

Android 客户端采用 Flutter 构建，短信接收、默认短信应用角色与系统通知等平台能力由最小化 Kotlin 原生模块实现，具体设计要求见 4.5。

基本功能包括：

- 新短信接收。
- 多 SIM 卡来源标识。
- 发送方和短信时间记录。
- 短信正文读取。
- 本地数据库存储。
- 分类任务调度。
- 网络恢复后自动补发。
- 应用进程被杀或设备重启后的消息恢复。

Android 客户端负责消息生命周期的初始管理，任何网络错误不得导致已经接收的消息丢失。

### 3.2 智能短信分类

收到短信后，由 PrivateSMS-Classifier 对文本执行分类。

分类输出至少包含：

- 短信类别。
- 类别置信度。
- 风险评分。
- 是否需要人工复核。
- 模型版本。

系统应同时保留模型原始预测结果和最终策略决策，便于用户纠错、审计和调试。

### 3.3 自动短信拦截

自动拦截是 PrivRelay 的核心功能之一。

#### 拦截处理策略

| 分类 | 默认处理建议 |
|---|---|
| Personal | 正常显示、同步 |
| OTP | 重要消息保护，不自动拦截 |
| Service | 正常显示、同步 |
| Transaction | 重要消息保护，不自动拦截 |
| Marketing | 达到用户设定条件后进入拦截箱 |
| Suspicious | 标记风险；满足策略条件时隔离 |
| Uncertain | 不自动拦截，正常保留 |

提供三种工作模式：

**模式 A：仅分类**

所有短信正常展示，分类器只负责提供标签与风险提示。

**模式 B：智能过滤**

识别营销短信，将符合策略的消息移入独立收件箱，不在正常消息列表中突出展示。

**模式 C：自动拦截**

用户主动启用后，系统可以将符合拦截条件的短信自动隔离，并抑制普通通知。

自动拦截由独立策略引擎执行，不能直接将 `is_spam = true` 等同于删除短信。

#### 拦截原则

1. 所有拦截记录均可查看。
2. 拦截结果可撤销，并支持恢复到正常收件箱。
3. 验证码、账户安全及交易通知采用额外保护规则。
4. 模型异常、超时或服务不可用时采用 Fail-open 策略。
5. 支持用户维护白名单、黑名单和自定义规则。
6. 自动拦截的阈值依据独立测试和用户配置确定，而不是直接使用未经真实数据校准的概率值。
7. 首版不执行永久删除短信的动作。

这里的“拦截”首先定义为应用层隔离与通知抑制，而不是运营商网络侧拦截。

如果需要真正控制 Android 系统短信的存储与通知行为，须按平台要求实现默认短信应用能力。当前实现已接入用户可选的默认 SMS 角色、SMS Provider、MMS 文本与最多 2 MiB 附件导入、E2EE 同步和 SENDTO 路由；超限附件保留在系统 Provider。未设置为默认的运行模式仍只能管理自身展示与跨设备推送，不保证能够拦截其他短信应用的系统通知。

### 3.4 跨设备消息同步

系统采用 Client-Server 架构。

支持 Android 手机与 Web、桌面端之间的消息同步。

功能要求：

- 实时消息推送。
- 历史消息查询。
- 消息去重。
- 断线自动重连。
- 离线消息补发。
- 多客户端同步状态管理。
- 设备撤销及会话过期处理。

消息投递采用持久化队列、幂等写入和确认机制实现至少一次传输条件下的有效去重。

### 3.5 Web 管理平台

Web 控制台包括：

**消息中心**

统一查看短信，支持分类筛选、搜索、归档及详情查看。

**拦截中心**

展示自动拦截记录、拦截依据、用户纠错及恢复操作。

**设备中心**

管理已授权手机、电脑和其他终端。

**规则中心**

配置过滤模式、白名单、黑名单和通知规则。

**运行监控**

查看在线设备数、同步状态、分类服务健康情况及错误记录。

### 3.6 用户反馈

用户可以修改短信分类结果，并提交本地纠错数据。

反馈处理流程：

1. 记录用户确认的正确类别。
2. 将纠错数据保存在受保护的本地数据库。
3. 区分待审核与已审核数据。
4. 生成聚合错误统计。
5. 经用户明确授权后，方可用于未来的模型评估或训练。

反馈行为不直接修改正在运行的模型参数。

## 4. 技术架构

### 4.1 总体设计

系统主要分为四个组成部分：

**Android Client**

基于 Flutter 构建（配合最小化 Kotlin 原生短信模块），负责短信采集、本地持久化、消息展示、离线队列及可用的端侧过滤能力。

**PrivRelay Server**

负责设备认证、消息同步、权限管理、策略执行和实时推送。

**PrivateSMS-Classifier**

负责模型推理、类别输出、风险评分和模型版本管理。

**Web Client**

负责跨设备消息展示、拦截管理、规则配置和用户操作。

### 4.2 推荐技术栈

| 模块 | 技术方案 |
|---|---|
| Android 客户端 | Flutter（Dart 3）+ Kotlin 原生短信模块 |
| 后端服务 | Go |
| 分类服务 | Python + FastAPI |
| 模型推理 | ONNX Runtime |
| 数据库 | PostgreSQL |
| 手机离线存储 | SQLite / Drift（SQLCipher 加密） |
| 前端 | Vue 3 + TypeScript |
| 实时同步 | WebSocket |
| API 通信 | REST / HTTPS |
| 部署 | Docker Compose |
| 反向代理 | Caddy / Nginx |
| 自动化测试 | Go Test / Pytest / Flutter Test / Kotlin 单元测试 |

第一版使用模块化单体后端，不引入不必要的微服务和复杂消息中间件。

### 4.3 消息处理流程

```text
Android 接收短信
        |
        v
本地持久化与生成消息 ID
        |
        v
网络可用时上传到自托管服务
        |
        v
PrivateSMS-Classifier 分类
        |
        v
策略引擎判断
        |
        +---- 正常消息 ------> 正常收件箱
        |
        +---- 重要消息 ------> 保护与提醒
        |
        +---- 营销消息 ------> 拦截箱
        |
        +---- 可疑消息 ------> 风险提示或隔离
        |
        +---- 无法确定 ------> 保留并允许复核
        |
        v
保存消息状态与处理结果
        |
        v
向其他授权设备同步
```

服务器端分类要求服务器能够读取待分类的短信正文。

因此，这属于可信自托管服务器架构，不应宣称为完整端到端加密。

未来可以通过端侧模型部署实现分类后加密同步。

### 4.5 Android 客户端（Flutter）设计要求

#### 4.5.1 技术路线与职责边界

Android 客户端统一采用 **Flutter** 实现界面、状态管理、本地数据、同步和用户交互逻辑。

Flutter 无法直接接收短信，也无法直接成为系统默认短信应用。因此客户端采用“**Flutter 主体 + 最小化 Kotlin 原生模块**”的结构：

- **Flutter / Dart 层：** 页面、路由、状态管理、本地数据库、待发送队列、网络同步、诊断信息。
- **Kotlin 原生层：** 短信广播接收、默认短信应用角色、SIM / 订阅信息、前台服务、系统通知与权限适配。

原生层只暴露稳定的 MethodChannel / EventChannel 接口，不承载可复用的业务规则。该边界必须在代码结构和测试中保持清晰，不得用 Flutter 掩盖 Android 平台限制。

#### 4.5.2 基础技术约束

| 项目 | 要求 |
|---|---|
| Flutter | stable 渠道，版本通过 FVM 固定并在 README 记录；Dart 3 |
| Android 版本 | minSdk 24；compileSdk / targetSdk 跟随发布时的最新稳定 Android SDK |
| UI | Material 3；支持深色模式、字体缩放和 TalkBack |
| 状态管理 | Riverpod（或经评审的等价方案）；业务状态不得散落在 Widget 内 |
| 路由 | go_router |
| 本地数据库 | Drift + SQLite；启用 SQLCipher 加密 |
| 密钥与令牌 | flutter_secure_storage，底层使用 Android Keystore |
| 网络 | Dio（REST）+ web_socket_channel（WebSocket） |
| 序列化 | json_serializable / freezed；接口模型必须有契约测试 |
| 国际化 | flutter_localizations + ARB，默认 zh-CN，预留 en |
| 构建 | dev / prod 两种 flavor；服务器地址通过 `--dart-define` 注入，不写入源码 |
| 依赖管理 | 提交 `pubspec.lock`；新增依赖需检查维护状态、许可证与权限影响 |

- Widget 不得直接访问 MethodChannel、数据库或 HTTP，统一经 repository / provider。
- `data/sync` 与原生 spool 的接口必须可使用 fake channel 进行单元测试。
- 原生 Kotlin 代码独立于 Flutter Widget 层，可单独编译和测试。

#### 4.5.4 短信采集要求

1. 使用 `RECEIVE_SMS` 运行时权限接收新短信；`READ_SMS` 仅在用户启用历史导入或默认短信应用模式时申请。申请前说明用途，用户拒绝后仍可查看已同步历史，不得崩溃或反复弹窗。
2. 原生 `BroadcastReceiver` 收到短信后，必须在返回前把原始记录写入**原生持久化 spool**（独立 SQLite 数据库或追加日志），再异步交给 Dart 层处理；不得依赖 Flutter 引擎处于存活状态。
3. spool 写入成功后，通过前台服务或 WorkManager 触发 Dart 消费入口（headless FlutterEngine）；引擎未能启动时保留记录，下次应用启动继续消费。
4. Dart 只有在 Drift 事务提交成功后，才按 spool id 幂等确认并删除对应记录；任一步失败均可重试，不得丢消息。
5. 采集字段至少包括：发送方、正文、接收时间（epoch 毫秒）、subscriptionId / SIM 槽位、运营商信息（可得时）、系统短信 id / thread id（可得时）、采集时间。
6. 在接收时生成客户端 `message_id`（UUIDv7 / ULID），上传时作为幂等键。
7. 去重键至少覆盖 `device_id + subscription_id + sender + received_at + body_hash`；同一短信重复投递不得产生两条业务消息。
8. 支持开机、应用升级、进程被杀和系统重启后的补偿处理；spool 中的原始记录在确认消费前不得清理。
9. 广播接收处理应在系统允许时间内完成（建议小于 5 秒），网络上传不得在 `onReceive` 中同步执行。
10. 非默认短信应用模式只管理本应用展示与同步，不承诺拦截其他短信应用的通知；该限制必须在设置页和 README 中说明。
11. 默认短信应用能力作为可选进阶模式，需完整实现短信写入系统数据库、通知和发送等平台要求，不与基础采集模式混用。
12. 客户端不直接依赖分类模型；分类结果以服务端返回为准，保留后续端侧推理的扩展点。

#### 4.5.5 本地存储与同步要求

1. 本地数据库是客户端 UI 的读取来源；网络不可用时，已同步数据仍可完整查看。
2. outbox 状态机为 `pending → uploading → acked / failed`；失败按指数退避加抖动重试，并区分网络错误、鉴权失败、服务端 4xx 和 5xx。
3. 上传批量大小可配置（建议不超过 50 条/批）；服务端逐条确认后再标记 `acked`。
4. 采用至少一次投递加服务端幂等去重；客户端重试不得产生重复业务消息。
5. 监听网络变化触发立即重试；WebSocket 断开后指数退避重连，重连成功后用游标拉取缺失消息。
6. 认证失败（401 / 403）时停止重试并进入“需要重新配对”状态，不自动清空本地历史；由用户确认后解绑并清理令牌。
7. 后台同步必须考虑 Doze：可选前台服务（常驻通知）保证实时性；未开启时使用 WorkManager 周期或加急任务补偿，禁止忙轮询。
8. 首版不依赖 FCM / GMS；在无 Google 服务的设备上，采集、本地查看和补发能力必须可用。
9. 设备配对使用 Web 控制台生成的一次性配对码或二维码；客户端生成 ECDSA P-256 密钥对并保存在 Keystore，注册请求必须签名。
10. 服务器地址必须由用户显式确认；非 HTTPS 地址默认拒绝，仅开发构建允许显式覆盖。
11. 设备被撤销后，后续请求返回未授权，客户端应提示并允许重新配对。
12. 提供本地数据保留与清理策略；用户可清除本地缓存和已上传记录。

#### 4.5.6 页面与交互要求

至少包含以下页面：

- **首次启动引导：** 隐私说明、权限申请、服务器地址、设备配对。
- **收件箱：** 分页加载（建议 50 条/页）、按分类筛选、搜索、下拉刷新和同步状态。
- **拦截箱：** 独立入口、拦截原因、恢复操作。
- **消息详情：** 正文、类别、置信度、模型版本、策略动作和纠错入口。
- **设备管理：** 本机信息、配对状态、撤销与解绑。
- **诊断：** 待发送数量、最近 ACK、分类服务健康状态、错误记录（不得包含正文）。
- **设置：** 通知、预览遮挡、后台同步、数据清理和关于。

交互约束：

1. 分类与风险使用文字加图标表达，不能只依赖颜色区分。
2. 验证码、交易类消息默认不在锁屏通知中展示正文，用户可在设置中调整。
3. 拦截和隔离动作必须在 UI 中可撤销。
4. 用户纠错写入本地 feedback outbox，按 3.6 的流程提交，不直接修改当前分类结果。
5. 网络异常和同步失败必须有可见但不打扰的状态提示。

#### 4.5.7 安全与隐私要求

1. 本地数据库启用 SQLCipher，密钥存储于 Android Keystore；限制或关闭 Android 自动备份，避免加密库与密钥不一致。
2. 访问令牌和配对密钥不得以明文写入 SharedPreferences、日志或崩溃报告。
3. Release 构建禁止输出短信正文、发送方、验证码等敏感日志；日志分级且可关闭。
4. 不集成会采集短信内容或设备标识的第三方分析 / 崩溃 SDK；如需诊断上报，必须自托管、脱敏并默认关闭。
5. 网络仅允许 HTTPS，`usesCleartextTraffic=false`；证书固定作为可选部署配置，不能默认写死。
6. Release 使用 R8、`--obfuscate --split-debug-info`；签名文件和口令不得入库。
7. 可选应用锁（生物识别 / PIN）与详情页防截屏（FLAG_SECURE）。
8. 权限最小化：除短信、通知、网络等必要权限外，不申请通讯录、定位、电话状态等无关权限。
9. 明确分发方式（自托管 / 侧载 / 应用商店）；使用受限 SMS 权限或默认短信应用角色时，须按 Google Play 政策准备说明和审核材料，不得虚假声明用途。
10. 在设置页和 README 中说明：非默认短信应用无法控制系统级短信通知；本地加密不等于服务端看不到正文。

#### 4.5.8 性能与稳定性目标

以下为工程目标，最终以测试报告为准：

- 冷启动到收件箱可交互：中端设备 P95 不超过 2.5 秒。
- 消息列表在 10,000 条数据下保持流畅，必须分页加载，不得一次性读取全部记录。
- 典型使用场景常驻内存低于 200 MB。
- 从收到广播到 spool 落盘：P95 不超过 500 毫秒。
- 正常联网下新消息端到端同步 P95 不超过 5 秒，与 8.3 保持一致。
- 测试期间不得出现阻断性 ANR；空闲时不得持续轮询或维持不必要的心跳。

#### 4.5.9 测试与发布要求

- `flutter analyze` 无 error，`flutter test` 全部通过。
- 单元测试覆盖：spool 消费、去重、outbox 状态机、重试策略、API 模型解析和权限状态机。
- Widget 测试覆盖：收件箱筛选、拦截箱恢复、纠错流程和设置项。
- `integration_test` 至少验证：配对 → 接收短信 → 上传 → 展示 → 恢复的完整链路。
- Kotlin 单元测试覆盖：PDU 解析、去重和 spool 写入。
- 真机测试矩阵：Android 7 / 10 / 12 / 14 / 15（并补充发布时的最新版本）中至少 3 个版本、双卡设备、Doze、断网 30 分钟、进程被杀、设备重启、权限拒绝和低电量场景。
- 发布产物包含 APK / AAB、符号表、构建说明和测试报告；构建过程必须可复现。

## 5. 安全与隐私设计

### 5.1 基本原则

1. 用户拥有数据控制权。
2. 不依赖商业云端 AI 接口。
3. 不在应用日志中记录完整短信正文。
4. 对验证码和交易信息实施额外保护。
5. 授权设备才能访问同步数据。
6. 支持用户主动删除本地及服务器数据。
7. 模型预测异常不应导致短信永久丢失。

### 5.2 设备认证

每个设备拥有独立身份。

新增设备通过用户确认完成配对。

撤销授权后，设备无法继续访问新消息。

历史数据的密钥撤销、清除和重新加密机制作为后续安全增强功能。

### 5.3 数据保护

采用 TLS 保护网络传输。

数据库应支持敏感字段加密、访问隔离及备份保护。

模型反馈数据与正式消息数据库分开管理。

严禁将真实私人短信、身份验证码或未经授权的反馈数据上传到公开 GitHub 仓库。

### 5.4 默认短信应用权限

Android 平台中，默认短信应用具有与普通短信读取应用不同的系统能力。

如果希望在手机端完整控制短信落库和通知，需实现符合 Android 要求的默认 SMS Handler。

Google Play 对 SMS 权限有严格的使用及审核条件。首版可以先定位为自部署、自用及测试分发，但必须保留明确的权限说明和授权机制。

## 8. 验收标准

### 8.1 功能验收

- 手机接收的测试短信能够正确进入系统。
- 消息分类服务能够稳定返回结果。
- 营销短信可以依据用户配置进入拦截箱。
- 重要短信具有优先保护规则。
- 被拦截的短信能够恢复。
- Web 端能够查看授权设备同步的消息。
- 手机断网后能够自动补发未同步短信。
- 服务重启、重试和网络抖动不产生重复入库。
- 未授权设备不能访问消息。

### 8.2 模型与拦截验收

PrivateSMS-Classifier 的当前版本可以作为实验性分类引擎直接集成。

自动拦截功能需要独立验收，关注：

- 营销短信拦截召回率。
- 正常短信误拦截率。
- 验证码和交易短信误拦截率。
- 不确定结果比例。
- 分类服务失败后的降级行为。
- 用户恢复拦截短信的操作结果。

在具备有代表性的独立测试数据前，不宣称当前模型达到某个确定的真实环境误拦截率。

自动拦截需用户主动开启，并默认保留原始短信与可恢复记录。

### 8.3 系统性能验收

建议采用以下工程目标：

- 正常联网情况下，跨设备同步 P95 延迟低于 5 秒。
- 离线恢复测试中的消息最终全部同步。
- 测试过程不产生重复业务消息。
- 单条短信推理延迟可统计、可复现。
- 分类服务异常不影响原始短信保存。
- 系统能够在普通 x86 CPU 服务器上稳定运行。

具体指标以测试报告为准，不使用未经实测的数据作为项目成果。

### 8.4 Android 客户端验收

- 全新安装后能够完成权限申请、服务器配置和设备配对。
- 应用进程被杀、设备重启或断网期间收到的短信不丢失，恢复后能够全部补发。
- 重复投递、重试和进程中断不会产生重复业务消息。
- 双卡设备能够正确记录每条短信的来源 SIM。
- 验证码和交易类短信不会进入自动拦截；被拦截短信可以恢复。
- 非默认短信应用模式下，系统级通知限制有明确提示，不夸大拦截能力。
- Release 构建的日志和诊断信息不包含短信正文、发送方或验证码。
- `flutter analyze`、`flutter test` 和关键 `integration_test` 通过，APK / AAB 可复现构建。

## 9. 项目创新点

### 9.1 智能分类与跨设备同步融合

将自训练中文短信分类模型接入完整的消息同步链路，实现从短信接收到分类、过滤、同步和人工纠错的统一流程。

### 9.2 面向隐私的自托管部署

支持用户自行管理服务器、短信数据和分类模型，降低对第三方云平台的依赖。

### 9.3 可恢复的智能自动拦截

区别于简单的黑名单过滤，实现基于模型类别、用户规则、白名单和安全保护策略的可恢复拦截系统。

### 9.4 离线优先的可靠消息同步

通过本地持久化队列、服务端幂等处理及状态确认机制，提高弱网和离线环境下消息同步的可靠性。

### 9.5 可扩展的分类器服务架构

将智能分类模型作为独立服务，与 Go 业务后端解耦，支持后续模型升级、部署优化和端侧推理扩展。

## 10. 开发约束与实施原则

项目开发应遵守以下要求：

1. **不重复训练现有模型**，优先复用已经完成的 PrivateSMS-Classifier。
2. 不将模型训练视为第一阶段开发重点。
3. 不修改现有模型权重，除非后续有明确的模型改进需求。
4. 分类服务和消息管理后端保持模块边界清晰。
5. 用户配置的自动拦截能力必须真实实现，不能只做前端效果。
6. 不允许因为推理失败而丢弃原始短信。
7. 所有自动拦截行为必须可审计、可查看和可恢复。
8. 不强制依赖 GPU、云端 LLM 或付费推理服务。
9. 优先完成可靠、可运行的核心功能，再扩展高级特性。
10. Android 客户端必须遵循 4.5 的 Flutter / Kotlin 边界；短信接收、默认短信应用和后台服务必须在真机验证，不能只依赖模拟器或插件默认行为。
11. 通过单元测试、集成测试和实际设备测试验证系统。

## 12. 项目最终目标

PrivRelay 的最终目标是提供一套**可独立部署、能够自动过滤短信、支持多设备安全同步、并保护用户隐私的完整软件系统**。

通过持续完善产品能力、可靠性和安全设计，最终形成既能够满足个人日常使用需求，也具有开源软件工程展示价值的作品。
